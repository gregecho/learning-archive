## 📚 Fundamental Concepts

### Elastic Load Balancing

ELB is a managed traffic distribution service that provides a single entry point with automatic high availability. There are four types, and the exam heavily tests the differences between them.

#### ALB — Application Load Balancer

Operates at layer 7 (HTTP/HTTPS). It is the most functional load balancer for modern applications. Supports HTTP, HTTPS, HTTP/2, and gRPC. Routing is based on configurable rules: path-based (prefix or exact match on URL), host-based (virtual hosting by hostname), query string, HTTP headers, and source IP.

**Target Groups**: ALB distributes traffic to target groups, which can be EC2 instances, ECS tasks, Lambda functions, or IPs (including on-premises via Direct Connect/VPN). Each routing rule points to a target group. A listener can have multiple rules with priority, and the default rule (default action) handles uncovered traffic.

**Weighted Target Groups**: supports weighted traffic distribution between two target groups. Useful for canary releases and blue/green deployments: send 95% to the old group and 5% to the new one gradually.

**Connection termination**: ALB terminates the SSL/TLS connection and communicates with targets on a new connection (with or without HTTPS). The `X-Forwarded-For` header carries the original client IP. If you need the real IP on the backend, configure X-Forwarded-For or use Proxy Protocol on ALB.

**Sticky sessions (Session Affinity)**: ALB can send requests from the same client always to the same target. The cookie can be generated by ALB (AWSALB) or by the target (application cookie). Useful when session state is in server memory — but the recommended practice is to externalize sessions in a cache like ElastiCache.

**Lambda as target**: ALB can invoke Lambda directly. This allows exposing a Lambda as an HTTP endpoint without API Gateway.

#### NLB — Network Load Balancer

Operates at layer 4 (TCP, UDP, TLS). Extremely efficient: tens of millions of requests per second with single-connection millisecond latency. Main feature: **static IP per AZ**. Can have one Elastic IP per AZ, which is essential for clients that need IP allowlisting in the firewall.

**Preserve source IP**: unlike ALB, NLB preserves the source IP by default on the target. This is important for compliance and firewalling scenarios.

**TLS Offload**: NLB can terminate TLS and use ACM certificates, if desired. If not terminated, it passes pure TCP traffic to the target.

**PrivateLink**: NLBs are the foundation of AWS PrivateLink. To expose a service to other accounts or VPCs privately, create an NLB and a VPC Endpoint Service.

**Static IP for firewall allowlist**: if the question mentions "client needs to allowlist IPs on corporate firewall" or "fixed IP per AZ," the answer is NLB.

#### GWLB — Gateway Load Balancer

Operates at layer 3 (IP) using the GENEVE protocol (packet encapsulation). Functions as an insertion point for virtual security appliances (firewalls, IDS/IPS, DPI) in the traffic path without the application noticing. Traffic is diverted to GWLB → appliance → returns to GWLB → continues to destination.

Typical configuration: traffic enters via Internet Gateway, is intercepted by GWLB (using VPC routing), processed by appliances in the GWLB endpoint's Target Group, and then routed to the final destination. Allows scaling appliances horizontally with ASG.

**When it appears on the exam**: scenarios mentioning traffic inspection with third-party security devices (appliances, next-gen firewalls such as Palo Alto or Fortinet) or centralized security in a dedicated security account.

#### CLB — Classic Load Balancer

Legacy. Operates at layers 4 and 7 in a limited way. The exam may mention it in a historical context, but never as the correct answer for new designs.

#### Cross-Zone Load Balancing

By default, each ELB node distributes traffic only to instances in its AZ. With cross-zone enabled, each ELB node distributes evenly to all targets in all AZs. ALB enables by default at no extra cost. NLB disables by default; when enabled, charges for inter-AZ transfer. GWLB also disables by default.

**Connection Draining (Deregistration Delay)**: period during which the ELB stops sending new connections to a target being removed, but maintains active connections until timeout. Default is 300 seconds. For instances with many long-lived connections, adjust this value.

### Auto Scaling Groups

ASG manages a fleet of EC2 instances, ensuring the desired capacity is maintained. It is intimately linked with ELB: ASG instances are regularly registered and deregistered in target groups.

#### Launch Templates vs Launch Configurations

**Launch Configurations**: legacy, immutable. To make any change, you need to create a new one. They do not support multiple instance types, Spot + On-Demand mixed, or ARM. Should be avoided in new projects.

**Launch Templates**: support versioning, multiple instance types, Spot and On-Demand mixing, instance families via $Latest and $Default, and base template inheritance. They are the preferred answer on the exam when the question mentions type diversification or Spot flexibility.

#### Scaling Policies

**Target Tracking Scaling**: defines a target metric (such as CPUUtilization = 60% or RequestCountPerTarget = 1000) and ASG automatically adjusts capacity to maintain that metric at the defined level. This is the simplest and most efficient policy for proportionally growing workloads. ASG automatically creates and manages CloudWatch Alarms.

**Step Scaling**: defines alarm ranges with different actions. Example: if CPU > 60%, add 1 instance; if CPU > 80%, add 3; if CPU < 30%, remove 1. Allows graduated response to varying intensity changes. Requires manual creation of CloudWatch alarms.

**Scheduled Scaling**: adjusts capacity at predefined times. Useful for predictable traffic patterns: increase at 8am, reduce at 8pm, Friday peaks. Can coexist with other policies.

**Predictive Scaling**: uses machine learning to analyze traffic history and provision capacity in advance. Advantage over Target Tracking: it is already ready before the peak arrives, rather than reacting afterward. Works best with at least 14 days of history. For the exam, it is the answer to the scenario "avoid scale-out lag before the daily peak."

#### Lifecycle Hooks

Lifecycle Hooks allow executing custom action during instance state transitions before the instance completes the transition.

**EC2_INSTANCE_LAUNCHING (Pending:Wait)**: the instance has been started but is not yet InService. During this period, you can run warm-up scripts, install monitoring agents, register in external systems. When finished, call `CompleteLifecycleAction(CONTINUE)` or let the heartbeat timeout expire.

**EC2_INSTANCE_TERMINATING (Terminating:Wait)**: the instance will be terminated. Before removal, you can collect logs, back up state, deregister from external IPAM. When finished, call `CompleteLifecycleAction(CONTINUE)` or `ABANDON`.

The lifecycle hook notification can be sent to SNS, SQS, or EventBridge, which then triggers Lambda for automation execution.

#### Health Checks

ASG determines if an instance is healthy via two types of health checks:

**EC2 health check** (default): based on instance hardware and network status reported by AWS. If the instance is in any state other than "running" or has an impaired instance check, ASG replaces it.

**ELB health check**: based on health checks configured in the target group (GET on a specific URL, expected response code). If the instance returns an unexpected response to ALB, it is marked as unhealthy. ASG with ELB health check enabled replaces instances that fail the ELB health check — much more comprehensive than just EC2 status.

**Recommendation**: always enable ELB health check on ASG when there is a Load Balancer. An instance that is "running" but has a frozen application passes the EC2 health check but fails the ELB health check.

### Warm-Up and Cooldown

**Instance Warmup**: period after scale-out during which the new instance gradually contributes to scaling metrics. Prevents ASG from continuing to add instances while new ones are still initializing. Supported in Target Tracking.

**ASG Cooldown**: waiting period after any scaling activity before initiating another. Prevents rapid oscillations. For step scaling, cooldown is separate for scale-out and scale-in actions.

### Termination Policy

ASG follows a selection logic to terminate instances on scale-in: first selects the AZ with the most instances, then within that AZ chooses based on the configured policy (default: oldest instance by launch template/config, then closest to the next billable hour). Custom policies available: OldestInstance, NewestInstance, OldestLaunchTemplate, ClosestToNextInstanceHour, and AllocationStrategy.

```text
Internet / Clients
       │
       ▼
  ┌──────────────────────────────────────────────────┐
  │          Elastic Load Balancer                   │
  │   ALB (HTTP/gRPC) | NLB (TCP/UDP) | GWLB (IP)   │
  │   Listeners → Rules → Target Groups              │
  └──────────────┬───────────────────────────────────┘
                 │  register / deregister
                 ▼
  ┌──────────────────────────────────────────────────┐
  │         Auto Scaling Group                       │
  │                                                  │
  │  Launch Template                                 │
  │  ┌──────────┐  ┌──────────┐  ┌──────────┐       │
  │  │  EC2 AZ-a│  │  EC2 AZ-b│  │  EC2 AZ-c│       │
  │  └──────────┘  └──────────┘  └──────────┘       │
  │                                                  │
  │  Scaling Policies: Target | Step | Scheduled     │
  │  Predictive: provisions before peak              │
  │  Lifecycle Hooks: Pending:Wait / Terminating:Wait│
  └──────────────────────────────────────────────────┘
                 │
                 ▼
         CloudWatch Alarms
                 │
                 ▼
         SNS / Lambda / EventBridge
```

## ⚙️ Important Exam Configurations

| Item | Default / Maximum value | Notes |
|---|---|---|
| Connection Draining (deregistration delay) | 300 seconds | Adjust for long connections |
| ALB idle timeout | 60 seconds | Connection closes if inactive |
| NLB static IP | 1 per AZ | Main differentiator vs ALB |
| ASG min/desired/max capacity | 0/0/0 by default | Configure per workload |
| ASG default cooldown | 300 seconds | Reduce for more agile scaling |
| Lifecycle Hook heartbeat timeout | 3,600 seconds | Adjustable per operation |
| ELB health check default interval | 30 seconds | Configurable per target group |
| Healthy threshold | 5 checks | Consecutive to mark healthy |
| Unhealthy threshold | 2 checks | Consecutive to mark unhealthy |

## 🔄 Service Comparison

| Feature | ALB | NLB | GWLB |
|---|---|---|---|
| OSI Layer | 7 (HTTP) | 4 (TCP/UDP) | 3 (IP) |
| Protocols | HTTP, HTTPS, gRPC | TCP, UDP, TLS | GENEVE |
| Static IP per AZ | No (DNS) | Yes (Elastic IP) | Yes |
| Preserve source IP | Via X-Forwarded-For | Native | Yes |
| Path/host based routing | Yes | No | No |
| Lambda as target | Yes | No | No |
| PrivateLink | No | Yes (base) | Yes |
| Traffic inspection with appliances | No | No | Yes |
| Cross-zone default | Yes (no cost) | No (charges inter-AZ) | No |

| Scaling Policy | When to use | Advantage |
|---|---|---|
| Target Tracking | Proportional and continuous workload | Simple, auto-managed alarms |
| Step Scaling | Differentiated response by intensity | Fine control by range |
| Scheduled | Predictable traffic pattern | Avoids lag in scale-out |
| Predictive | Recurring and predictable peaks | Provisions before peak |

## 💡 Exam Tips and Pitfalls

- ALB has dynamic IP (DNS). If the client needs a fixed IP on the firewall, the answer is NLB with Elastic IP.
- GWLB does not distribute application traffic — it inspects and forwards. Confusing it with ALB is a trap.
- ASG with only EC2 health check will keep instances with frozen applications, since the instance is "running." Enable ELB health check.
- Target Tracking creates CloudWatch alarms automatically. Do not delete these alarms — they are service-managed.
- Launch Configuration is legacy and immutable. In any new question, Launch Template is the preferred answer.
- Lifecycle Hook on scale-out serves for warmup before entering service; on scale-in, for state draining before shutdown.
- Cross-zone balancing on NLB has inter-AZ transfer cost. If the question mentions cost, evaluate whether cross-zone is necessarily enabled.
- Predictive Scaling requires 14 days of history to work well. For new environments, Target Tracking or Scheduled is more appropriate.

## 💡 For the Exam

- HTTP/gRPC, path routing, Lambda target → ALB. TCP/UDP, fixed IP, PrivateLink → NLB. Third-party security appliance → GWLB.
- Predictable peak = Scheduled + Predictive. Proportional workload = Target Tracking. Graduated response = Step Scaling.
- Always enable ELB health check on ASG in production.
- Launch Template surpasses Launch Configuration in all new scenarios.
- Lifecycle Hooks = automation before entering service or before leaving.
