**1.** A company has an ALB and wants to register `api.company.com` pointing to it. The root domain (`company.com`) needs to point to the same ALB. Which record type should be used for the root domain?

- A) CNAME record pointing to the ALB DNS
- B) A record pointing to the ALB IP
- C) Alias record pointing to the ALB
- D) NS record delegating to the ALB

<details>
<summary>Answer</summary>
**C — Alias record**
CNAME **cannot** be used at the root domain (zone apex) — it is a DNS limitation. Alias is a Route 53 extension that works at the apex and points to AWS resources (ALB, CloudFront, S3, API Gateway, etc.) at no additional query cost. The ALB IP is dynamic — never use a direct A record for ALB.
</details>

**2.** A global application needs to route users to the AWS region with the lowest latency. Which Route 53 routing policy should be used?

- A) Geolocation routing
- B) Latency-based routing
- C) Weighted routing
- D) Geoproximity routing

<details>
<summary>Answer</summary>
**B — Latency-based routing**
Latency routing measures latency between the client and each AWS region and redirects to the region with the lowest latency. Geolocation routes based on geographic location (country/continent) — does not measure actual latency. Geoproximity routes based on geographic distance (can have configurable bias) via Traffic Flow.
</details>

**3.** Which Route 53 routing policy is used for A/B testing, sending 10% of traffic to a new application version?

- A) Failover routing
- B) Latency routing
- C) Weighted routing
- D) Multivalue routing

<details>
<summary>Answer</summary>
**C — Weighted routing**
Weighted allows assigning weights (0-255) to multiple records. For 10%/90%: record A with weight 10, record B with weight 90. Useful for canary deployments, blue/green testing, gradual migrations. The sum of weights defines the proportion; weight 0 removes the record from rotation without deleting it.
</details>

**4.** A company has an application in us-east-1 (primary) and ap-southeast-1 (backup). They want automatic failover. Which Route 53 configuration?

- A) Weighted routing with 90/10 weight
- B) Failover routing with Health Check on the primary region
- C) Latency routing (automatic for lowest latency)
- D) Multivalue routing with 2 records

<details>
<summary>Answer</summary>
**B — Failover routing with Health Check**
Failover routing defines a PRIMARY record and a SECONDARY record. Route 53 uses Health Checks to monitor the primary; if it fails, it automatically responds with the SECONDARY. This is the standard pattern for Active-Passive DR. Health Check can monitor an endpoint, another route, or a CloudWatch Alarm.
</details>

**5.** A company wants to serve static content (images, CSS, JS) from S3 via CloudFront with maximum security, without making the S3 bucket public. What is the currently recommended AWS mechanism?

- A) Origin Access Identity (OAI) with bucket policy
- B) Origin Access Control (OAC) with bucket policy
- C) Signed URLs on CloudFront
- D) S3 presigned URLs generated by Lambda

<details>
<summary>Answer</summary>
**B — Origin Access Control (OAC)**
OAC is the successor to OAI (launched in 2022). It supports S3 in all regions, SSE-KMS, additional HTTP methods, and S3 Object Lambda. The bucket needs a bucket policy allowing the CloudFront distribution ID via OAC. OAI still works but is considered legacy. The bucket remains private.
</details>

**6.** A streaming site needs to serve premium paid content only to authenticated users via CloudFront. Which mechanism should be used?

- A) WAF with authentication rule
- B) CloudFront Signed URLs or Signed Cookies
- C) OAC with restrictive bucket policy
- D) CloudFront Geo Restriction for non-paying countries

<details>
<summary>Answer</summary>
**B — Signed URLs or Signed Cookies**
Signed URLs: for a specific file per user (specific video-id). Signed Cookies: for multiple files or all premium content (Netflix-style). Signed with a private key by the backend; CloudFront validates with the key pair. OAC protects S3, not end users. WAF does not authenticate users.
</details>

**7.** What is the difference between CloudFront Functions and Lambda@Edge?

- A) CloudFront Functions support only Viewer Request/Response; Lambda@Edge also supports Origin Request/Response
- B) CloudFront Functions have < 1ms latency and lower cost; Lambda@Edge is more powerful (Node.js/Python, up to 10s)
- C) Lambda@Edge can access the request body; CloudFront Functions cannot (on Viewer Request)
- D) All of the above are true

<details>
<summary>Answer</summary>
**D — All are true**
CloudFront Functions: only Viewer Request/Response, JavaScript, sub-millisecond, < $0.0000001, no body access. Lambda@Edge: supports 4 events including Origin Request/Response, Node.js/Python, up to 30s (Origin), up to 5s (Viewer), can access body. Lambda@Edge = complex cases (auth, rewrite, A/B); CF Functions = simple transformations (headers, redirect).
</details>

**8.** A company wants to block access to CloudFront for countries on a denylist. Which feature should be used?

- A) WAF with Geographic Match rule
- B) CloudFront Geo Restriction (Allowlist or Denylist)
- C) Route 53 Geolocation routing with NXDOMAIN
- D) Lambda@Edge checking X-Forwarded-For

<details>
<summary>Answer</summary>
**B — CloudFront Geo Restriction**
CloudFront Geo Restriction uses the MaxMind GeoIP database to block (Denylist) or allow only (Allowlist) specific countries — returns HTTP 403. WAF Geographic Match also works but has additional cost and is more complex. Route 53 Geolocation would be bypassable. Geo Restriction is the native and simplest solution.
</details>

**9.** What is the main difference between Route 53 and AWS Global Accelerator for improving global performance?

- A) Route 53 uses anycast IPs; Global Accelerator uses DNS
- B) Global Accelerator uses 2 Static Anycast IPs and routes through the AWS backbone; Route 53 uses DNS-based routing
- C) Route 53 has lower latency; Global Accelerator is cheaper
- D) Global Accelerator only works with ALB; Route 53 works with any endpoint

<details>
<summary>Answer</summary>
**B — Correct**
Global Accelerator: 2 Static Anycast IPs, traffic enters the nearest AWS edge and travels through the private AWS backbone to the endpoint. Benefit: does not depend on DNS TTL, failover in seconds, IP consistency (firewall whitelisting). Route 53: DNS-based, depends on TTL propagation for failover, IP changes. For: non-HTTP or fixed IP requirement → GA. For simple HTTP/S routing → Route 53.
</details>

**10.** A company uses CloudFront and notices that an S3 content update does not appear for users. What should be done immediately (without waiting for TTL to expire)?

- A) Delete and recreate the CloudFront Distribution
- B) Create an Invalidation in CloudFront for the affected file or path
- C) Enable S3 versioning and create a new version
- D) Change the TTL to 0 at the Origin

<details>
<summary>Answer</summary>
**B — CloudFront Invalidation**
Invalidation forces edge caches to discard specific objects (e.g., `/images/logo.png` or `/*`). The new edge request results in a cache miss and fetches the current version from the origin. First 1,000 invalidation paths per month are free; after that there is a cost. Best long-term practice: use file versioning (asset hashing) to avoid invalidations.
</details>

**11.** An application service needs Health Checks for an internal resource in a private subnet (without a public IP). How to configure a Health Check in Route 53?

- A) Not possible — Route 53 only monitors public endpoints
- B) Create a Health Check of type "CloudWatch Alarm" based on private resource metrics
- C) Use a Calculated Health Check combining other HCs
- D) Install the Route 53 Health Check Agent on the private instance

<details>
<summary>Answer</summary>
**B — CloudWatch Alarm Health Check**
Route 53 Health Checkers operate from the public internet and cannot reach private resources. To monitor private resources: create a custom CloudWatch metric, configure an Alarm, and create a Route 53 Health Check based on that Alarm. When the Alarm fires → Health Check fails → DNS failover activated.
</details>

**12.** A company wants to use WAF to protect its API on API Gateway against SQL Injection and XSS attacks. Which configuration should be used?

- A) WAF Classic with IP-based rules
- B) AWS WAF v2 with AWS Managed Rules (AWSManagedRulesCommonRuleSet)
- C) Shield Standard integrated with API Gateway
- D) Security Groups on API Gateway

<details>
<summary>Answer</summary>
**B — AWS WAF v2 with Managed Rules**
AWS WAF v2 can be associated with API Gateway, ALB, CloudFront, and AppSync. AWSManagedRulesCommonRuleSet includes protections against SQL injection, XSS, and other OWASP vulnerabilities. AWS keeps the rules updated. Shield Standard protects against network-layer DDoS, not SQL injection. API Gateway does not have Security Groups.
</details>

**13.** What is "Resolver" in Route 53 and what is its function?

- A) Service that resolves DNS names to IPs outside of AWS
- B) Route 53 Resolver DNS for VPC + Inbound/Outbound Endpoints for hybrid DNS
- C) Component that converts Route 53 names into aliases for AWS resources
- D) Global DNS propagation debugging tool

<details>
<summary>Answer</summary>
**B — Route 53 Resolver with Endpoints**
Route 53 Resolver answers DNS queries within the VPC (169.254.169.253). For hybrid DNS: **Inbound Endpoint** allows on-premises to resolve AWS names (DNS queries arrive from on-prem into the VPC); **Outbound Endpoint** allows the VPC to resolve on-premises names (via forwarding rules to on-prem DNS servers via DX/VPN).
</details>

**14.** A content platform uses CloudFront. How to force all traffic to use HTTPS (redirect HTTP to HTTPS)?

- A) Configure the S3 bucket to redirect HTTP→HTTPS
- B) In the CloudFront Behavior: Viewer Protocol Policy = "Redirect HTTP to HTTPS"
- C) In the CloudFront Distribution: Force SSL/TLS via ACM always
- D) Use Lambda@Edge to inspect and redirect

<details>
<summary>Answer</summary>
**B — Viewer Protocol Policy in Behavior**
Each CloudFront Behavior has "Viewer Protocol Policy" with options: HTTP and HTTPS, Redirect HTTP to HTTPS, or HTTPS Only. Setting "Redirect HTTP to HTTPS" makes CloudFront return 301 for HTTP requests → HTTPS automatically. This is the native configuration, no Lambda@Edge needed.
</details>

**15.** Which DNS record type is required for ACM certificate domain validation and for receiving email?

- A) CNAME (for ACM) and MX (for email)
- B) TXT (for ACM) and NS (for email)
- C) A record for both
- D) Alias (for ACM) and SPF record (for email)

<details>
<summary>Answer</summary>
**A — CNAME (ACM) and MX (email)**
ACM (AWS Certificate Manager) offers domain validation via CNAME: you add the CNAME generated by ACM to your DNS and AWS verifies periodically. MX records point to email servers (e.g., SES, Office 365, Google Workspace) and are required to receive email on the domain. TXT records are used for SPF/DKIM/domain verification in other services.
</details>
